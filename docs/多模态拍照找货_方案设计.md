# 多模态「拍照找货」方案设计

> 状态：**已实现（B+ 混合方案）**
> 定位：PRD Phase 4 加分项 —— 多模态交互之「拍照找货」
> 前置事实：经实测，当前 Ark 模型 endpoint（`ARK_MODEL`）**本身支持视觉输入**，
> 同一个 endpoint 既能处理文本对话、也能读图。无需新接入视觉模型。
> 另：现有 `ARK_EMBEDDING_MODEL` 走 `/embeddings/multimodal`，**能编码图片**
> （2048 维，与文本同空间，已实测同款图自相似 0.9996），故视觉重排零新增基础设施。

---

## 实现状态（B+ 落地）

采用 **路线 B + 轻量视觉重排** = B+ 混合方案：VLM 抽 query 走文本 RAG（主召回）
+ 图片向量对候选做视觉相似度重排。落地文件：

| 层 | 文件 | 作用 |
|----|------|------|
| 视觉能力 | `backend/llm/vision.py` | `vision_extract_query`（VLM 看图出中文 query）、`embed_image`（图→2048维向量）|
| 离线索引 | `backend/rag/build_image_index.py` | 100 张商品图编码 → `backend/storage/image_index.json`（`python -m rag.build_image_index`）|
| 在线打分 | `backend/search/visual_index.py` | `VisualIndex` 单例，余弦打分/重排（暴力，无 ANN）|
| 图搜逻辑 | `backend/agent/tools/recommend.py` | `run_image`：文本召回池 + 视觉重排融合（`final=α·文本+β·视觉`）|
| 流式入口 | `backend/agent/orchestrator.py` | `handle_image_turn_stream`：看图→抽词→重排检索→composer，绕过 router |
| API | `backend/api/main.py` | `ChatRequest.image_base64/image_url`；`/chat/stream` 有图走图搜 |
| 前端 | `client/.../GuideView.swift` 等 | 相机(`UIImagePickerController`)/相册(`PhotosPicker`) → 压缩 base64 → 气泡缩略图 |

可调环境变量：`VISUAL_TEXT_WEIGHT`(默认0.6)、`VISUAL_IMAGE_WEIGHT`(默认0.4)、
`VISUAL_POOL_SIZE`(默认12)、`ARK_VISION_TIMEOUT`。

降级：视觉索引缺失/图片编码失败 → 自动退化为纯文本排序；VLM 无法识别 → 友好澄清不检索。

## 0. 先搞清楚：这里的「多模态」到底指什么

「模态」= 信息的形式。文本、图片、语音、视频都是不同模态。

我们现在的系统是**单模态**：用户只能打字（文本），Agent 理解文本 → 检索 → 回文本+商品卡。

「多模态」就是让**输入/输出不止文本**。本项目范围内三个方向：

| 方向 | 输入模态 | 现状 |
|------|---------|------|
| 语音输入（ASR） | 语音 → 文本 | 已做（前端 SpeechInput）|
| **拍照找货** | **图片 → 商品** | **本文档要做的** |
| TTS 播报 | 文本 → 语音 | 未做 |

所以「拍照找货」的本质是：**用户给一张图，系统找出库里长得像 / 同类 / 相关的商品**。
难点只有一个 —— 图片不能直接拿去和文本商品库比较，必须先把图片「翻译」成系统能检索的东西。

怎么翻译？这就引出你问的核心问题。

---

## 1. 核心抉择：图片要不要「向量化匹配」？两条路线对比

你问的「是否可以向量化去匹配，还是走别的流程」——这正是图搜的两大主流路线。
两条都能做，但工程量和效果差别很大。

### 路线 A：图像向量化匹配（CLIP 式 / 以图搜图）

把图片和商品图都编码成**同一个向量空间**里的向量，然后算相似度找最近的。

```text
用户图片 ──► 图像 Encoder ──► 向量 [0.1, -0.3, ...]
                                      │
商品图(100张) ──► 图像 Encoder ──► 向量库  │ 算余弦相似度
                                      ▼
                              最相似的 Top-K 商品
```

- **优点**：真正的「以图搜图」，能抓视觉相似（同款、相似外观）。
- **缺点（对本项目而言很重）**：
  1. 需要一个**图像 embedding 模型**（如 CLIP / 中文 Chinese-CLIP）。我们现在的
     `ARK_EMBEDDING_MODEL` 是**纯文本** embedding，**不能编码图片**。要么再接一个
     图像 embedding 服务，要么本地跑 CLIP（增加依赖、显存、离线模型）。
  2. 需要**单独建一套图像向量索引**（把 100 张商品图全部编码入库），和现在的
     文本 Chroma 库**不互通**，是另一条独立检索链路。
  3. 现有的 **rerank（智谱 rerank-pro）是文本精排**，对图文相似度无能为力，
     这条链路的质量保证要重做。
  4. 纯视觉相似 ≠ 用户意图。用户拍一件黑色 T 恤，可能想要「同款」也可能想要
     「类似但更便宜的」，纯向量距离表达不了这种业务偏好。

### 路线 B：VLM 抽取 → 复用现有文本检索（推荐）

不直接对图片做向量。先用**视觉大模型（VLM）把图片「看懂」并描述成文本检索意图**，
再把这段文本喂进我们**已经跑通的文本 RAG 链路**。

```text
用户图片 ──► VLM(现有 Ark 模型) ──► 结构化检索意图
                                   "黑色 男士 纯色 短袖T恤"
                                   {category:服饰运动, color:黑, ...}
                                        │
                                        ▼
                          现有 search_service（零改动复用）
                          understand_query → Chroma 向量召回 → rerank
                                        │
                                        ▼
                                  Top-K 商品卡片
```

- **优点**：
  1. **复用 90% 现有代码** —— 文本检索、rerank、商品聚合、流式输出全不动。
  2. **不需要新模型、不需要图像向量库** —— 现有 Ark endpoint 已支持读图（已实测）。
  3. VLM 抽取的是**语义意图**（类目+属性+品牌），天然贴合「找同类商品」这种
     电商意图，而不是死板的像素相似。
  4. 可解释：能告诉用户「我从图里看到了黑色短袖 T 恤，为你找了这些」。
- **缺点**：
  1. 找的是「**同类/相关**」而非「**视觉同款**」。但对本项目 100 个 SKU 的库
     和 demo 目标，这恰恰是想要的效果。
  2. 多一次 VLM 调用（~1-2s）。可接受。

### 结论

| 维度 | A 图像向量 | B VLM 抽取 |
|------|-----------|-----------|
| 新增模型 | 需要图像 embedding | **不需要**（复用现有）|
| 新增向量库 | 需要建图像索引 | **不需要**（复用文本 Chroma）|
| 复用现有链路 | 几乎不能 | **90% 复用** |
| rerank 质量保证 | 要重做 | **现成可用** |
| 工程量 | 大 | **小** |
| 贴合电商意图 | 一般 | **好** |
| demo 收益 | 中 | **高** |

**采用路线 B（VLM 抽取 → 文本检索）。** 路线 A 的「以图搜图」可作为后续探索方向，
但不是首期该投入的地方 —— 它的成本主要花在搭建一条全新的图像检索基础设施上，
而 demo 收益并不比 B 高。

## 2. 端到端流程（路线 B）

```text
┌─────────┐   ① 选图/拍照      ┌──────────────┐
│  iOS 端 │ ────────────────► │  图片 base64  │
│ Composer│                    └──────┬───────┘
└─────────┘                           │ ② POST /chat/stream (带 image)
                                       ▼
                          ┌────────────────────────────┐
                          │ FastAPI /chat/stream        │
                          └──────────────┬──────────────┘
                                         │ ③ 有图 → 先走 VLM 抽取
                                         ▼
                          ┌────────────────────────────┐
                          │ llm.client.vision_extract() │
                          │  图片 → 检索 query + 属性     │
                          └──────────────┬──────────────┘
                                         │ ④ 把 query 当普通文本喂进 Agent
                                         ▼
                          ┌────────────────────────────┐
                          │ orchestrator → recommend    │
                          │ search_service（完全复用）   │
                          └──────────────┬──────────────┘
                                         │ ⑤ 商品卡片 + 解说，SSE 流式
                                         ▼
                                    iOS 端渲染
                          （用户气泡显示缩略图 + "找到这些相似商品"）
```

### 关键点：图片只在「入口」处转成文本，之后链路完全不知道有图片存在

这是 B 路线优雅的地方 —— 图片在最前面被 VLM 转成文本检索意图后，
后面的 orchestrator / search_service / composer 看到的就是一句普通的中文 query，
和用户手打「黑色男士短袖T恤」没有任何区别。所以这些模块**一行都不用改**。

## 3. 图片怎么传给后端：base64 vs URL

| 方式 | 做法 | 适用 |
|------|------|------|
| **base64 直传**（推荐 demo）| 前端把图压缩后编码成 base64 字符串，放进 SSE 请求体 | 无需对象存储，最简单，单图够用 |
| 上传对象存储拿 URL | 先 PUT 到 TOS，拿回 URL，再把 URL 传后端 | 多图/大图/生产环境，省带宽 |

**建议首期用 base64 直传**：

- 不依赖额外的对象存储上传链路。
- 单张商品图压缩到 ~1024px、JPEG 0.7 质量后通常 100-300KB，base64 后 ~200-400KB，
  放在一次 POST 里完全可接受。
- VLM 接口同时支持 `image_url`（远程 URL）和 `data:image/jpeg;base64,...`（内联 base64），
  所以 base64 能直接喂给模型，无需中转。

> 注意：base64 不能走 `EventSource`（GET，URL 长度受限），但本项目 `/chat/stream`
> 已经是 **POST + 手动读流**（见 FrontendServices），天然支持请求体带大字段。

## 5. VLM 抽取 prompt 设计要点（实现时参考）

让 VLM 输出**可检索的中文 query**，而不是泛泛描述。约束：

- 只描述**商品本体**：类目、子类目、颜色、材质、风格、明显品牌 logo；忽略背景/人/手。
- 输出一句自然的中文检索语，贴合用户会怎么搜，例：`黑色男士纯色圆领短袖T恤`。
- 看不清或非商品图时，输出空 / 提示「没看清商品，换张清晰点的？」，不要硬编。
- 可选：同时返回结构化字段（category / color / brand）写进 trace，便于解释和排查。

## 6. 风险与降级

| 风险 | 降级策略 |
|------|---------|
| VLM 看错/看不清 | 抽取为空时提示用户重拍，或回退让用户补一句文字 |
| 图片过大/超时 | 前端强制压缩到 ≤1024px、JPEG 0.7；后端对 base64 大小设上限 |
| 库内无相似商品 | 复用现有「零命中放宽条件」降级（见 TODO 的 search fallback）|
| VLM 调用失败 | 不阻断：提示「图片识别暂时不可用，试试文字描述？」|

## 7. 落地顺序建议

1. **后端贯通（先验证）**：写 `vision_extract` + `/chat/stream` 接图，用脚本/curl
   传一张图，确认能走通「图 → query → 商品卡片」。这步不碰前端，最快验证可行性。
2. **前端接入**：相机/相册选图 → 压缩 → base64 → 发送 → 气泡显示缩略图。
3. **体验打磨**：解说文案点明「根据你上传的图片…」，加载态、错误态。
