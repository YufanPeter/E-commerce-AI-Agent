# CartPilot 后续优化计划

更新日期：2026-11-09  
状态：已确定以本地 `amazon_dense_10k` 为主商品语料；首阶段接入见后端 README。下文多轮修复、检索对照与量化验收仍是后续工作。

当前优先顺序：先在 Amazon 目录上建立可重复的中文检索和详情基线，再围绕同一语料修复多轮约束、指代和澄清，最后比较 BM25、向量召回、融合和重排。旧商品库独立用于多规格及交易回归；正式检索评测需重新标注 Amazon 商品 ID。

## 1. 清理后的起点

本次已将已跟踪文件恢复到当前 Git 提交，删除未跟踪的实验脚本、评测集、报告和测试缓存，不保留本轮实验备份。原有已提交代码、文档和测试保留；本地 `.env`、依赖环境及商品数据库未删除。清理后唯一新增文件为本计划。

此前未提交的模型接口兼容性改动也已撤销。保留密钥配置不等于恢复后的代码能够正确使用它：当前聊天客户端仍读取 `ARK_API_KEY`、`ARK_BASE_URL` 和 `ARK_MODEL`，后续首先要核对 DeepSeek 与其他服务的配置映射。

现有项目已经有路由、检索、工具执行、回复生成、会话和购物车存储，可以沿用。下一阶段重点是让每轮用户意图准确落到商品、规格和约束，并用最终执行结果验证成功。扩大商品库有助于提高检索实验的区分度，但不会自动解决多轮状态错误。

## 3. P0：恢复清晰的 API 配置与可观测性

相关入口：`backend/llm/client.py`、`backend/llm/vision.py`、`backend/search/search_service.py`、`backend/api/main.py`。

- 聊天模型接入 DeepSeek；Embedding、Rerank、Vision 按各自服务单独配置密钥、地址和模型。避免切换聊天模型时误切向量模型或图片模型。
- 使用统一配置读取与启动校验，错误提示明确区分缺少配置、认证失败、模型不存在、限流、超时和响应格式错误。日志不得记录密钥。
- 先测试最小聊天请求、路由结构化返回、Embedding 维度和 Rerank 排序；图片能力独立检查，不作为文字评测的前置依赖。
- 保留每次调用的模型标识、耗时、重试次数和失败类型；限制超时与重试预算。工具失败时返回可恢复状态，不能在回复中宣称操作成功。
- 检查普通 HTTP、SSE 和前端展示的结果是否一致，尤其是工具失败、澄清和购物车写入之后。

## 4. P1–P3：优先修复 Multi-turn

### 4.1 规格修改与待完成的购物任务

当前 `backend/agent/tools/cart.py` 会把待补充任务中的旧 `spec_text` 与新输入拼接。这样的文本合并无法清晰表达“保留颜色、覆盖尺码”等操作，应改成字段级状态更新。

计划保存明确的商品 ID、规格字段、数量、缺失字段和任务阶段：

- “换成 L”覆盖尺码；“红色不变，换大一号”保留颜色，并基于当前选中 SKU 和商品尺码顺序计算。没有当前尺码、没有相邻尺码或对应规格缺货时，说明原因并请求必要信息。
- 区分选择商品、补规格、改数量、取消任务和开始新任务。新任务不得继续沿用旧商品的待办状态。
- 写入前核对商品、SKU、数量、库存及本轮最新要求；写入成功后才完成待办任务。失败时保留可恢复信息，不产生重复添加。
- 工具结果、会话状态、数据库和界面展示使用同一执行结果；回复生成器只能描述已经发生的操作。

重点入口：`backend/agent/tools/cart.py`、`backend/agent/session.py`、`backend/store/cart_store.py`。

### 4.2 统一目标解析与澄清恢复

当前 `backend/agent/orchestrator.py` 调用工具时统一传入空 `slots`。后续应建立明确的工具参数契约，传递解析后的目标、规格更新和约束，而不是让每个工具独立猜测。

- 保存最近展示的有序商品列表、视图类型及版本，区分推荐列表、对比列表和购物车列表。“第二个”必须对应用户刚刚看到的列表。
- 保存当前聚焦商品及其来源；统一解析序号、商品名称、“这个”“那个红色的”“刚才那款”。型号中的数字不能被误当成列表序号。
- 查询改写用于辅助理解和检索；执行目标以明确选择和经过校验的状态为准，工具再次检查目标是否属于有效候选。
- 缺少目标或存在多个合理目标时，保存待办动作和待补字段，提出具体澄清问题；用户回答后继续原任务。
- 明确的选择直接执行，测量过度澄清率。取消、换话题或候选列表更新时，显式处理旧待办状态。

重点入口：`backend/agent/tools/reference.py`、`backend/agent/tools/resolve.py`、`backend/agent/tools/product_detail.py`、`backend/agent/tools/compare.py`、`backend/agent/orchestrator.py`。

### 4.3 偏好与硬约束

当前查询合并逻辑会保留部分旧条件；需要区分“没有提及”和“明确撤销”。对每个字段支持保留、新设值、清除三种操作。

- “只看 Nike”设置品牌约束；“品牌都行”清除品牌约束；“不要 Nike”设置排除条件。包含与排除冲突时按明确的最新要求更新。
- “预算改成 800”替换原上限；“预算不限”清除上限。区分当前购物任务的约束和用户长期偏好，避免临时条件永久生效。
- 切换品类时清除不适用的规格与任务条件；是否继承预算、品牌等通用偏好须有明确规则。
- 在最终返回商品和实际 SKU 上校验硬约束，统计违反比例。没有满足条件的商品时说明无结果，放宽条件需要用户明确选择。

重点入口：`backend/search/query_understanding.py`、`backend/search/where_builder.py`、`backend/search/search_service.py`、`backend/store/user_memory_store.py`。

验收覆盖至少包括：相对尺码变化、颜色保留、旧规格覆盖、同名商品、型号数字、推荐/购物车序号切换、待办取消、澄清后恢复、品牌清除、预算变化、跨品类切换、无结果与缺货。已知错误写入回归用例必须全部通过，但不能据此声称所有真实场景都正确。

## 5. P4：更换更大的 Amazon 数据集

### 5.1 两条数据路线，各自回答不同问题

| 数据路线 | 主要用途 | 使用边界 |
| --- | --- | --- |
| Amazon Reviews 2023 | 商品目录、介绍和带来源的评论知识 | 缺少导购意图标签和多轮对话标签，需另外构造并审核 |
| Amazon Shopping Queries / ESCI | 有相关性标注的检索与候选重排评测 | 检索数据不能直接作为多轮任务完成率测试集 |
| 内部交易场景数据 | 规格选择、库存边界、购物车和澄清恢复测试 | 明确标注为构造数据；不得把模拟库存说成 Amazon 实际库存 |

Amazon Reviews 2023 的元数据包含商品名称、特征、描述、类目、价格等；价格是抓取时的美元价格，评论与商品元数据使用 ASIN/parent ASIN 等标识关联。实际导入字段和缺失率以下载版本为准。[官方数据说明](https://amazon-reviews-2023.github.io/)

ESCI 提供 query–product 相关性标签 Exact、Substitute、Complement、Irrelevant，包含英语、日语和西班牙语；其示例与商品表按 `product_id` 和 `product_locale` 关联，并提供 train/test 划分。公开标注针对候选商品列表，不能默认所有未标注商品都不相关。[官方仓库与数据结构](https://github.com/amazon-science/esci-data)

### 5.2 导入步骤与适配

1. **先做小批量样本审计。** 选择一个或两个适合导购的品类，筛出约 1,000 个具有必要字段的有效商品，记录去重、缺失率、属性覆盖及来源；跑通后扩到约 10,000 个。数量为计划规模，不是当前规模。
2. **建立统一商品模型。** 保留内部 ID、来源 ID、ASIN/parent ASIN、locale、标题、品牌、类目、描述、属性、价格、币种及数据版本。缺失信息保持未知，不通过模型补成商品事实。
3. **区分知识证据与交易事实。** 评论保留来源并标记为用户意见；不能从评论推断当前价格、库存或官方规格。每个商品先选少量高质量评论，避免海量重复内容稀释检索。
4. **单独处理 SKU 和库存。** 颜色、尺码文本不等于完整可购买 SKU 表。公共数据缺少的信息采用明确隔离的模拟交易夹具，或在产品中显示未知；订单只能按实际实现能力定义。
5. **适配语言与币种。** 先以英语、美国 locale 做公共检索评测，价格明确为 USD，界面与预算解析同步支持币种。中文测试另行审核；翻译测试不能称为真实中文用户查询。
6. **分离公共与内部评测语料。** ESCI 评测优先使用其自身商品表；若与 Reviews 目录关联，核查父子 ASIN、locale 和缺失匹配，报告覆盖率，不能默认两个数据集能完整拼接。
7. **建立可复现索引。** 规范化事实进入 SQLite，知识片段进入向量与词法索引；记录语料版本、Embedding 服务/模型/维度、分块与索引配置。更换向量模型时完整重建，不混用不同模型向量。
8. **采用独立导入与切换。** 在新的数据库和索引中验证后再切换；保留原已提交的小型样例，避免把开发样例与正式评测语料混在一起。导入前核对来源许可和使用要求。

可扩展现有 `backend/store/import_product_data.py` 和 `backend/rag/build_chroma.py`，增加适配器与数据校验；无需首先更换全部存储和检索架构。

## 6. P5：重新建立可信的量化评测

以下样本数均为后续目标，不是已完成实验。开发回归集用于修复，最终测试集在调优前冻结；同一模板的近似改写尽量放在同一划分，避免泄漏。人工审核标签与合理答案，AI 辅助构造的场景明确标注为合成数据。

### 6.1 Intent routing

- 按当前真实的 7 个工具类别定义标签：`recommend`、`refine`、`compare`、`product_detail`、`cart`、`clarify`、`fallback`。计划主测试集 350 条，每类 50 条；依赖上下文的样例附带前置状态。
- 另设 100 条困难样例，覆盖错别字、口语、省略、混合意图和边界场景。混合意图先定义执行优先级或允许标签，不能事后按模型输出改答案。
- 报告 overall accuracy、macro-F1、每类样本数/precision/recall、confusion matrix，以及困难集成绩。
- 对比结构化路由与单 prompt 文本分类，使用相同模型、上下文、标签规则和调用预算；明确允许的解析与重试。分别报告原始路由准确率、输出契约合规率及最终经状态规则处理后的执行路由准确率。
- 如果对照没有显示提升，应如实报告。结构化返回格式更稳定，不等于语义分类必然更准。

### 6.2 Retrieval pipeline

- 明确定义 keyword baseline：使用现有词法检索中的 BM25，固定分词、索引字段、参数和候选数；报告实际纳入的 query 数量及每条 relevance judgment 来源。
- 对比 BM25、vector-only、完整 pipeline，并分别去掉 reranking、RRF fusion、structured filtering。保持语料和其他设置不变，记录候选预算；只有测到收益后才声称组件有贡献。
- 公共 ESCI 先区分候选重排实验与全库检索实验。NDCG 的标签增益、Recall 的相关性阈值和未标注结果处理在运行前固定；候选集指标不能直接解释为全库召回能力。
- 内部约束查询单独提供价格、品牌、属性等可检查判断，评估 filtering 的贡献和约束违反率。相关商品总数应来自可复核的标签或完整条件匹配。
- 报告 Recall@5、NDCG@5、Hit@1、MRR@5，附组件消融的绝对差值；说明无相关商品或无结果查询的处理方式。
- 检索延迟报告 p50/p95，明确包含的查询理解、Embedding、召回、融合和 rerank 阶段；另报完整 Agent 响应延迟。记录冷/热缓存、并发、失败及重试口径，不能把检索耗时写成整个购物任务耗时。

### 6.3 Multi-turn 上下文管理

| 指标 | 计划样本与覆盖 | 判分依据 |
| --- | --- | --- |
| 指代消解准确率 | 至少 100 条，覆盖序号、属性、名称、焦点切换、跨视图和缺少目标等约 10 类场景 | 工具最终使用的目标 ID 与审核标签一致；可确定目标与需要澄清的样例分开统计 |
| 多轮任务完成率 | 至少 100 个会话，覆盖选购、比较、补规格、修改、加购、取消及无匹配情况 | 会话最终状态、SKU、数量和数据库结果满足预先定义的目标；不只看回复措辞 |
| 模糊输入检出 | 至少 50 个需澄清场景及 50 个明确输入 | 同时报 precision、recall 和误澄清率，避免“全部澄清”得到虚高检出率 |
| 澄清后恢复率 | 对需澄清样例提供固定用户补充答案 | 分别报告被正确检出后的条件恢复率，以及全部模糊场景最终成功率 |
| 偏好正确应用率 | 至少 50 个会话、100 个带标签的检查点 | 返回商品及实际动作满足该轮有效偏好，覆盖新增、覆盖、清除、排除和跨品类切换 |
| 平均完成轮数 | 使用相同任务集与统一最大轮数预算 | 报成功任务平均轮数，同时给出失败比例和全部会话轮数分布，避免只展示容易成功的任务 |

另设至少 30 个规格修改用例，重点覆盖相对尺码、保持颜色、覆盖旧规格、缺货、取消及重复请求。

多轮 baseline 必须写清楚状态差异：

- 无上下文版本不读取对话历史、聚焦商品、待办状态和继承偏好；保留正常的商品与购物车数据库。使用相同工具、任务和调用预算。
- 追加“仅原始历史文本、无显式状态管理”的对照，判断结构化上下文管理是否优于单纯把历史交给模型。
- 从同一初始快照开始，每个实验会话隔离用户和购物车，固定补充答案；失败也计入分母。缺货和无匹配任务按事先定义的合理终点判分，不要求系统虚构可购买商品。

### 6.4 证据、稳定性与简历使用

- 每例保存标签、数据版本、模型配置、路由决策、状态更新、工具参数、执行结果、耗时和错误类型。最终评分以结构化结果和实际存储为主，人工复核争议样例。
- 先通过针对性离线回归，再做少量真实 API 冒烟测试，最后运行冻结测试集。模型或数据变化后才运行必要的新对照，记录变动范围。
- 比较使用相同的模型版本、商品库、参数和预算。对模型随机性做重复测量，报告波动或置信区间及 API 失败比例、每任务调用数和成本。
- 简历可以写“在 N 条人工审核的构造测试/公开评测查询上达到 X，并相对指定 baseline 提升 Y 个百分点”。只有新实验完成且可复核后填入数字。
- 构造场景的任务完成率不能表述为真实线上转化率；公开英文检索成绩不能表述为中文多轮导购成绩；单个组件改善不能表述为整个 Agent 的普遍提升。

## 7. 暂缓事项与下一次交付

暂缓 RL 微调、全面替换向量数据库、同时接入所有 Amazon 类目及大规模图片扩展。先用受控对照确认状态、工具契约和检索质量的实际瓶颈，再决定是否需要这些投入。

下一次实施交付应先包含：独立的模型服务配置、一个能够完整恢复与修改规格的购物链路、统一目标解析、偏好清除规则及对应回归用例。随后交付 Amazon 导入适配、冻结评测集和三组指标报告。任何“已修复”“有效提升”或简历数字，都以对应验收与实验结果为依据。
