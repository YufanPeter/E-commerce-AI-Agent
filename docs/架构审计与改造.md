# 架构审计与改造

> 日期：2026-11-07。原则：能用的不大改，改动要有评测数字支撑。

## 1. 结论

分层架构本身是对的，不需要重写。真正的问题集中在两处：

- **解析结果没有校验。** 模型输出直接变成硬过滤，导致加上过滤后召回反而下降。
- **记忆是一张没接上线的表单。** 页面上一半的字段没有任何代码使用，预算却被当成硬过滤。

## 2. 各层审计

| 层 | 判断 | 这次做了什么 | 还没做 |
| --- | --- | --- | --- |
| API | 够用 | 新增 `/memory/*` 接口，对话时记录行为事件 | **没有鉴权**，知道 user_id 就能读取或清空记忆；购物车仍是单用户 |
| 编排 | 够用，不动 | 无 | compare 会覆盖 `last_hits`，对比后说「第三个」指不到 |
| 工具 | 够用，不动 | 推荐结果带上用到了哪些记忆 | 推荐理由仍只看标题，命中的证据没有传给 composer |
| 话术 | 够用，不动 | hint 里说明用了哪些记忆、用户的长期情况 | 同上 |
| 检索 | 骨架对，校验缺失 | 见第 3 节 | 只验证过 100 个商品，扩库要改成两段式召回 |
| LLM | 够用，不动 | 无 | 无 |
| 记忆 | 重做 | 见第 4 节 | 订单不落库，「上次买的」还做不到 |
| 客户端 | 记忆页重做 | 见第 5 节 | 无 |

## 3. 召回评测

题库和脚本在 `backend/evals/`：

```bash
cd backend
python -m evals.run_recall                                         # 开发集
python -m evals.run_recall --cases evals/recall_heldout.jsonl --label heldout   # 留出集
python -m evals.run_memory                                         # 记忆抽取
```

- **开发集**：129 题，用来定位问题和调规则，分数偏乐观。
- **留出集**：71 题，规则定稿后才写，只看数字不看错题，这个分数才可信。
- 结构化题的标准答案由 SQL 推导，其余为人工标注。

### 证据定位（开发集 38 题，锁定商品后找 FAQ 或评价）

目标 chunk 全部进入前 6 条，`product_detail` 正是取前 6 条给话术，所以这一段不用改。精排对 FAQ 的 Hit@1 有帮助（0.82 到 0.96），对评价反而变差（1.00 到 0.60），因此没有给详情页加精排。

### 根因和修复

| 现象 | 根因 | 修复 |
| --- | --- | --- |
| 「敏感肌能用的防晒」返回空 | 模型把想要的属性填进排除词 | 排除词必须在原话里被否定过 |
| 「无酒精的卸妆油」返回空 | 商品写着「无酒精」也被子串命中 | 识别文本里的否定说法 |
| 「无糖茶」返回空 | FAQ 和评价里的对比说法被当成分 | 普通排除只看商品描述 |
| 「红腰子」只出兰蔻 | 模型猜品牌后硬过滤 | 品牌必须是用户说出来的 |
| 「神仙水」进了精华类 | 模型猜错子类目后硬过滤 | 用商品名和品牌实际覆盖校验 |
| 「扫地机器人」返回手机 | 库外词被就近归类 | 模型标记 + 商品文本校验 + 相关性门槛 |
| 部分手机进不了候选 | 前 50 条 chunk 被少数商品占满 | 每个商品最多 4 条 |

### 建议

- **本地打开精排。** `.env` 现在是 `USE_RERANK=0`，留出集 Hit@1 是 0.91，打开后 0.96。我没有改你的配置。
- **解析保留快模型。** `qwen-flash` 和默认模型召回完全一致，开发集平均每题快约 1 秒。

### 这些数字的局限

- 商品库只有 100 个，向量召回本来就容易。扩到几千个后 R@5 会下降，到时要改成两段式召回并重跑。
- 相关性门槛 `SEARCH_WEAK_MATCH_DISTANCE=0.44` 是在这个库和这个向量模型上定的，换了要重定。
- 标注是我做的，没有第二人复核。

## 4. 记忆层

### 旧版的问题

- 喜欢的品牌、价格倾向、补充偏好存了但没有任何代码读取。
- 说过一次「预算 500」，之后搜笔记本就一条结果都没有。
- 类目写成「食品生活」，库里是「食品饮料」，关注这个类目后硬过滤直接为空。
- 「推荐通勤的双肩包」会被记成长期偏好。
- 同时记着「喜欢华为」和「不买华为」。

### 现在的设计

| 来路 | 怎么生效 |
| --- | --- |
| 你明确说的（规则抽取） | 立即生效，可撤销 |
| 模型听出来的 | 不挡商品的立即生效；会挡商品的（不买某品牌、忌讳）先问你 |
| 过敏和忌口 | 永远先问你 |
| 从行为推测的 | 永远先问你；未确认时只有品牌给很小的排序加权 |

- **硬约束只有两种：** 不买的品牌、确认过的忌讳。其余都只影响排序，超预算的商品还能看到。
- **台账：** 每条记忆有来源、原话、使用次数。旧的偏好 JSON 和接口保留，两边自动对齐。
- **行为事件：** 搜索、看详情、对比、加购、下单。推测有依据（「最近加购 2 次」），按 30 天半衰期衰减。
- **作用域：** 「买手机一般 3000 以内」只对手机成立。

## 5. 记忆页

从「一张要填的表单」改成「导购记得你什么」：

- 用一句话告诉它，不用填表。
- 每条记忆显示你的原话和它怎么起作用，比如「硬性排除，不会再推荐」。
- 猜出来的先问，给出依据，可以点「记住」或「不对」。点了「不对」不再提。
- 删除可撤销，清空要二次确认。
- 一个开关暂停全部个性化，记忆不会丢。
- 去掉了写死的用户名「Lily」，连不上服务时明确提示并可重试。

已在模拟器上跑通：发送一句话、确认过敏建议、删除、撤销，并核对后端数据一致。

## 7. 下一步

我建议：先把证据传给 composer（推荐理由最能摆脱 toy 感），再做订单落库（「再买一次」的前提），鉴权在上线前必须做。

## 8. 已知限制

- 行为事件只记录对话里发生的动作。在购物车页直接操作、在 App 里点开详情都不算，因为这些接口不带 user_id。
- `comparison.py` 仍按「食品生活」取维度，食品对比走通用维度。离线索引也只有通用维度，改名后要重建索引才有意义，所以没动。
