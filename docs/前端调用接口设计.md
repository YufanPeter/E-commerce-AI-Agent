# CartPilot 前端调用接口设计

本文档定义 iOS 前端需要预留的调用边界，目标是让当前 SwiftUI 原型后续可以平滑接入 RAG Agent 后端、多模态上传、商品库、购物车与下单流程。

对应 Swift 代码：

- `client/AIShoppingGuide/APIModels.swift`：前后端共享的数据契约
- `client/AIShoppingGuide/FrontendServices.swift`：前端 service protocol
- `client/AIShoppingGuide/MockFrontendServices.swift`：本地 mock 实现

## 设计原则

1. 前端不直接持有模型 API Key，所有 LLM/RAG 调用都走后端。
2. 商品价格、库存、优惠、规格必须来自商品服务或 RAG 检索证据，不能由模型自由生成。
3. 对话返回采用流式事件，文本、商品卡、对比表、澄清问题、工具调用结果都作为结构化事件进入 UI。
4. 购物车和下单作为结构化 CRUD 能力暴露，支持 Agent 通过工具调用驱动前端状态变化。
5. 多模态附件先上传获取 file token / URL，再随 Agent 请求发送。

## 前端 Service 划分

| Service | Swift protocol | 后端职责 |
| --- | --- | --- |
| Agent | `AgentServicing` | 对话、RAG 检索、流式回复、工具调用编排 |
| Product | `ProductServicing` | 商品详情、搜索、对比数据 |
| Cart | `CartServicing` | 购物车 CRUD、订单预览、确认下单 |
| Profile | `UserProfileServicing` | 用户偏好、默认地址、排除项 |
| Media Upload | `MediaUploadServicing` | 图片/语音上传票据、文件落库 |
| Analytics | `AnalyticsServicing` | 推荐点击、加购、反馈、错误埋点 |

## 2. 商品接口

### `GET /v1/products/{product_id}`

返回 `ProductPayload`。商品详情页必须优先使用该接口刷新价格、库存、规格和图片。

### `GET /search`（RAG 检索 + 零命中降级）

当前后端已实现（`backend/api.py`）。把自然语言 query 走完整 RAG 链路
（意图理解 → SQLite 硬匹配 → Chroma 召回 → CrossEncoder 精排 → 商品聚合），
**零命中时按品类放宽阶梯自动降级**，保证 demo 不出现空结果。

> 说明：原规划的 `POST /v1/products/search`（带 `filters` 结构化过滤）作为后续演进，
> 当前 demo 以本接口为准——硬过滤由后端从 query 解析，前端只传自然语言。

Query 参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `q` | string | 是 | 自然语言检索 query，需 URL 编码 |
| `limit` | int | 否 | 返回商品数上限，默认 10，范围 1–50 |

Response（200）：

```json
{
  "requestID": "search",
  "query": "5000以内非苹果笔记本",
  "matchType": "fallback",
  "fallbackReason": "未找到完全匹配的商品，已放宽：价格区间",
  "relaxedFilters": ["price"],
  "products": [
    { "productID": "p_digital_004", "title": "...", "price": { "display": "¥6299 起" }, "score": 0.90 }
  ],
  "parsed": { "category": "数码电子", "sub_category": "笔记本电脑", "brand_exclude": ["Apple 苹果"], "max_price": 5000 }
}
```

字段说明：

- `matchType`：`"strict"` = 完全匹配；`"fallback"` = 零命中后放宽得到的兜底结果。
- `fallbackReason`：`strict` 时为 `null`；`fallback` 时是给用户看的中文说明（解释放宽了什么）。
- `relaxedFilters`：机读的放宽维度列表，取值 `price` / `brand_exclude` / `brand_include` / `sub_category` / `full_vector`。
- `products[]`：复用 `ProductPayload`，额外带 `score`（rerank 排序分，越高越相关）。
- `parsed`：LLM 解析出的结构化意图，前端一般不展示，用于调试与"为什么这么推"的解释。

**前端处理要求（重要）**：

1. **严格匹配与 fallback 必须视觉区分，禁止合并进同一列表。** 后端保证二者互斥
   （一次响应只会是 `strict` 或 `fallback`），前端据 `matchType` 分区渲染：
   - `strict`：正常商品列表。
   - `fallback`：列表上方插一条提示条，文案取 `fallbackReason`，例如
     “未找到完全匹配的商品，已放宽：价格区间。以下为相近推荐”。
2. `products` 为空且 `matchType=fallback`：放宽到底仍无结果（例如指定了不存在的护肤品牌，
   而该品类策略绝不放品牌），前端展示空态 + `fallbackReason`，不要静默空白。
3. 错误响应：上游 LLM / 检索异常返回 `502 { "code": "SEARCH_UPSTREAM_FAILED", "retryable": true }`，
   按可重试错误处理。

放宽阶梯（后端 `search_service.py`，前端无需实现，仅供理解 `relaxedFilters` 含义）：

- 默认顺序：价格 → 品牌排除 → 指定品牌 → 子类目上推大类 → 全库纯向量召回（每层更宽）。
- 品类定制（`relaxation_priority` 的静态兜底，后续可由 LLM 按品类注入）：
  - **美妆护肤 / 奢侈品：绝不放品牌**，且不做全库召回（宁可返回空也不串品牌），阶梯仅 价格 → 子类目。
  - 手机 / 笔记本：价格优先放宽（默认即如此）。
  - 食品饮料：子类目可优先放宽（口味/品类替代性强）。
- `negative_ingredients`（如“不要含酒精”）是用户硬约束，**任何层级都不放宽**。

已验证触发例：

| query | matchType | relaxedFilters | 返回 |
| --- | --- | --- | --- |
| `300以上的Nike跑鞋` | strict | `[]` | Nike Pegasus 41 |
| `5000以内非苹果笔记本`（最低非苹果 6299） | fallback | `["price"]` | 联想 / 华为（仍排除 Apple） |
| `始祖鸟800-1500徒步鞋`（始祖鸟无货） | fallback | `["price","brand_include"]` | 萨洛蒙 / 迈乐 |

### `POST /v1/products/compare`

Request:

```json
{
  "productIDs": ["p_001", "p_002"],
  "focus": "哪个更保湿"
}
```

Response 使用 `ProductComparisonPayload`：

- `products`：参与对比的商品
- `rows`：参数行，如价格、容量、材质、评价、适合场景
- `values[].isHighlighted`：前端用于高亮更优项
- `recommendation`：最终推荐结论

## 3. 多模态上传

### `POST /v1/uploads/tickets`

Request:

```json
{
  "intent": "visualSearch",
  "mimeType": "image/jpeg",
  "sizeBytes": 283941
}
```

Response:

```json
{
  "uploadID": "upload_123",
  "uploadURL": "https://upload.example.com/upload_123",
  "expiresAt": "2026-05-22T12:00:00Z",
  "headers": { "Content-Type": "image/jpeg" }
}
```

前端上传成功后构造 `AttachmentPayload`，随 Agent 请求发送：

```json
{
  "id": "upload_123",
  "kind": "image",
  "mimeType": "image/jpeg",
  "remoteURL": "https://cdn.example.com/upload_123.jpg",
  "metadata": { "width": "1280", "height": "960" }
}
```

## 4. 购物车接口

### `GET /v1/cart`

返回 `CartSnapshotPayload`。

### `POST /v1/cart/mutations`

Request 使用 `CartMutationRequest`：

```json
{
  "action": "add",
  "productID": "p_001",
  "skuID": "sku_001",
  "selectedOptions": { "容量": "120g" },
  "quantity": 1,
  "selectedCartItemIDs": []
}
```

支持动作：

- `add`
- `updateQuantity`
- `updateSpecification`
- `remove`
- `select`
- `deselect`
- `selectAll`
- `clearSelection`

Response：最新 `CartSnapshotPayload`。

## 5. 下单接口

### `POST /v1/orders/preview`

Request:

```json
{
  "selectedCartItemIDs": ["cart_item_001", "cart_item_002"]
}
```

Response：`OrderPreviewPayload`，包含商品行、默认地址、价格汇总和库存/价格变更 warnings。

### `POST /v1/orders/{order_id}/confirm`

Request:

```json
{
  "addressID": "address_default"
}
```

Response：`OrderConfirmationPayload`。

## 6. 用户偏好接口

### `GET /v1/profile`

返回 `UserProfilePayload`。

### `PATCH /v1/profile`

Request 使用 `UserProfileUpdateRequest`，支持局部更新预算、品类、排除项、属性和默认地址。

### `GET /v1/profile/addresses`

返回地址列表。前端只展示脱敏手机号。

## 7. 埋点与反馈接口

### `POST /v1/analytics/events`

Request:

```json
{
  "name": "product_card_tap",
  "properties": {
    "productID": "p_001",
    "sessionID": "session_123",
    "source": "agent_message"
  },
  "createdAt": "2026-05-22T12:00:00Z"
}
```

建议事件：

- `agent_message_send`
- `agent_stream_error`
- `product_card_tap`
- `product_add_to_cart`
- `cart_item_select`
- `order_preview_create`
- `recommendation_feedback`

## 8. 前端接入顺序

P0：

1. 用 `AgentServicing` 替换 `GuideView.simulateResponse`
2. 用 `ProductServicing` 替换商品详情页本地 Product
3. 用 `CartServicing` 替换 `RootView` 内本地购物车数组
4. 加入统一错误模型 `APIErrorPayload`

P1：

1. 接入 `MediaUploadServicing`，完成图片上传找货
2. 接入 `ProductComparisonPayload`，渲染结构化对比表
3. 接入 `UserProfileServicing`，让偏好参与检索排序

P2：

1. 接入 `AnalyticsServicing`
2. 支持 WebSocket 双向会话
3. 支持 TTS/ASR 状态事件

## 9. 安全与配置

- 模型 API Key 只允许保存在后端或本地未提交配置中，禁止进入 iOS bundle。
- 前端只配置后端 base URL，例如 `https://api.cartpilot.example.com`。
- 所有接口都应返回 `traceID`，方便定位 RAG 检索和模型调用问题。
- 商品价格、库存、优惠必须带 `updatedAt`，前端展示时以后端结果为准。
